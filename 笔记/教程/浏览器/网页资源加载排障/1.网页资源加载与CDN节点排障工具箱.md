# 网页资源加载与 CDN 节点排障工具箱

这份教程用于处理一类常见问题：页面主体能打开，但控制台大量 JS、CSS、图片或字体资源报 `ERR_CONNECTION_TIMED_OUT`、`ERR_CONNECTION_RESET`、`ERR_SSL_PROTOCOL_ERROR` 等错误。

配套脚本已迁移到当前目录的 [scripts](./scripts/)：

| 脚本 | 用途 | 推荐入口 |
| --- | --- | --- |
| [flush-restart-chrome.cmd](./scripts/flush-restart-chrome.cmd) | 双击调用 PowerShell 版清 DNS 并重启 Chrome | 日常优先 |
| [flush-restart-chrome.ps1](./scripts/flush-restart-chrome.ps1) | 可读源码版，便于审计和修改 | 修改逻辑时使用 |
| [flush-restart-chrome.bat](./scripts/flush-restart-chrome.bat) | 内嵌 PowerShell 的单文件版本 | 需要单文件分发时使用 |
| [diagnose_page.py](./scripts/diagnose_page.py) | 抓页面并提取所有子资源，按主机检查 DNS/TCP/HTTPS | 定位问题资源主机 |
| [diagnose_cdn.py](./scripts/diagnose_cdn.py) | 对可疑主机逐 IP 检查 TCP/TLS/HTTP 状态 | 判断 CDN 节点是否部分异常 |

相关原理见：[网页资源加载失败的分层排障方法](../../../学习记录/网络排障/1.网页资源加载失败的分层排障方法.md)。

## 适用场景

- 首页 HTML 能返回，但页面白屏或功能不可用。
- DevTools 里大量静态资源超时或被重置。
- 同一网站有时能打开、有时不能打开。
- 换网络、换代理、清缓存后表现不一致。
- 怀疑 CDN 某些边缘节点、DNS 缓存或浏览器连接池命中了坏节点。

不适合用这套脚本直接判断的场景：

- 后端接口业务报错，例如 401、403、500。
- 页面脚本逻辑异常，例如 `TypeError`、`ReferenceError`。
- 需要登录态、复杂交互或验证码才能加载资源的页面。

## 快速修复：清 DNS 并重启 Chrome

当问题表现为“刚才还能用，刷新后大量资源超时”，可以先用重启式清理排除浏览器缓存和连接复用影响。

双击运行：

```text
scripts\flush-restart-chrome.cmd
```

它会执行：

1. 定位本机 Chrome 安装路径。
2. 对带窗口的 Chrome 进程发送关闭信号，尽量让 Chrome 保存会话。
3. 执行 `ipconfig /flushdns` 清理系统 DNS 缓存。
4. 使用 `--restore-last-session` 重新打开 Chrome。

注意事项：

- 运行前保存正在编辑的表单、文档和后台页面。
- 如果 Chrome 弹出“关闭多个标签页”确认框，需要手动确认。
- 这个方案只是在客户端重新解析和重连，不会修复服务端或 CDN 节点本身的问题。

## 定位问题资源主机

先用 `diagnose_page.py` 看页面依赖了哪些资源主机，以及哪个主机在 DNS、TCP 或 HTTPS 层失败。

安装依赖：

```powershell
pip install requests urllib3
```

运行默认目标：

```powershell
cd /d D:\file_save\workspace\note_cloud\笔记\教程\浏览器\网页资源加载排障\scripts
python diagnose_page.py
```

换成自己的目标站点：

```powershell
python diagnose_page.py https://example.com/
```

指定代理：

```powershell
python diagnose_page.py https://example.com/ http://127.0.0.1:7897
```

重点看输出中的两段：

- `涉及主机清单`：资源数最多的主机通常最值得优先排查。
- `逐主机可达性`：任一主机出现 `DNS FAIL`、`TCP443 FAIL`、`HTTPS FAIL`，都说明故障已经定位到资源主机层。

判断方式：

| 输出现象 | 说明 | 下一步 |
| --- | --- | --- |
| DNS 失败 | 域名无法解析 | 检查 DNS、代理规则、hosts |
| TCP443 失败 | 443 端口连不上 | 检查网络、代理、机房或防火墙 |
| TCP443 成功但 HTTPS 失败 | TCP 通，但 TLS/证书/HTTPS 有问题 | 使用 `diagnose_cdn.py` 逐 IP 检查 |
| 所有主机都成功 | 问题可能在具体路径、鉴权、缓存或前端加载时机 | 回到浏览器 Network 面板继续查 |

## 检查 CDN 多节点稳定性

当 `diagnose_page.py` 发现某个资源主机 HTTPS 异常，继续用 `diagnose_cdn.py` 检查它的每个解析 IP。

```powershell
python diagnose_cdn.py download.example.com
```

指定一个实际资源 URL：

```powershell
python diagnose_cdn.py download.example.com https://download.example.com/assets/app.js
```

输出分三段：

| 段落 | 用途 | 判读 |
| --- | --- | --- |
| A. 走代理拉资源 | 判断代理路径是否稳定 | `ok` 多、`bad` 少说明代理路径可用 |
| B. 直连拉资源 | 判断本地直连是否稳定 | 直连失败而代理成功，优先看网络或路由 |
| C. 逐 IP | 判断 CDN 节点是否部分异常 | `HTTP/1.1 200 OK` 是可用节点，重置或超时是异常节点 |

如果同一个域名解析出多个 IP，只有部分 IP 失败，就很可能是 CDN 边缘节点状态不一致。浏览器并发加载大量资源时，一旦命中异常节点，就会表现为随机白屏、随机超时或只坏一部分静态资源。

## 修复与绕过方案

| 方案 | 操作 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 清 DNS 并重启浏览器 | 运行 `flush-restart-chrome.cmd` | 偶发命中坏 IP 或旧连接 | 只是临时绕过 |
| 调整代理规则 | 将异常资源域名走稳定代理线路 | 本机直连不稳定，代理稳定 | 依赖代理可用性 |
| hosts 固定可用 IP | 将域名指向 `diagnose_cdn.py` 验证过的好 IP | 急需确定性访问 | CDN IP 轮换后需要维护 |
| 反馈服务方 | 提供异常 IP、时间、错误类型 | CDN 节点或证书配置异常 | 修复周期取决于服务方 |

hosts 示例：

```text
203.0.113.10 download.example.com
```

修改 hosts 后需要执行：

```powershell
ipconfig /flushdns
```

并重启浏览器。

## 迁移到其他业务场景

替换目标时通常只需要改三处：

- `diagnose_page.py` 的目标 URL：传命令行第一个参数。
- `diagnose_page.py` 的代理 URL：传命令行第二个参数，或按需修改脚本默认值。
- `diagnose_cdn.py` 的主机名和资源 URL：传命令行参数，优先选择真实失败的 JS/CSS 文件。

脚本保留了原始默认值，方便追溯来源案例。用于其他系统时，建议总是显式传参，避免误以为默认站点就是当前目标。
